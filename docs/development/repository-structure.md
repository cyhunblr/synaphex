## Top level

```text
synaphex/
├── src/                    product source
│   ├── mcp/                MCP protocol surface
│   ├── operations/         use-case commands behind each tool
│   ├── core/               services and invariants
│   ├── domain/             types, errors, role contracts
│   ├── providers/          provider adapters
│   ├── infrastructure/     process, state, Git, locks
│   ├── installer/          `synaphex` CLI and MCP registration
│   └── index.ts            internal re-export barrel
├── test/                   test suite
│   ├── fixtures/
│   └── live/               manual real-provider validation
├── scripts/
│   ├── ci/                 packed-product smoke, fake provider CLI
│   └── release/            preflight, registry state, prepare
├── docs/
├── .github/workflows/      ci.yml, release.yml
├── package.json
└── package-lock.json
```

Build output goes to `dist/` (and `.test-dist/` for compiled tests). Both are gitignored. **`dist/` is never the source of truth** — it is regenerated by `npm run build`, and reading it to understand behavior will eventually mislead you.

## Source directory map

### `src/domain`

Types, error classes, role contracts, execution-policy and agent-result shapes.

**Belongs here:** anything that describes *what things are* — type definitions, error classes, immutable contract tables, pure predicates.

**Does not belong here:** filesystem access, process spawning, MCP types, provider specifics. This layer imports nothing from the rest of `src/`, and that must stay true.

### `src/infrastructure`

Mechanics: `process-runner.ts`, `state-store.ts`, `isolated-git-runner.ts`, `recoverable-process-lock.ts`, `process-entrypoint.ts`.

**Belongs here:** how to spawn a process, write state atomically, run Git in isolation, hold a lock.

**Does not belong here:** any decision about *whether* something should happen. This layer also imports nothing from the rest of `src/`.

### `src/core`

The services that hold the invariants — routing, invocation, role contracts, rules, staging coordination, apply management, task/session/plan/memory managers.

**Belongs here:** rules that must hold regardless of how they were requested.

**Does not belong here:** MCP schemas, provider argument construction, terminal I/O.

### `src/operations`

Use-case commands sitting between the tool surface and core services.

**Belongs here:** orchestration of a single user-visible operation — resolve inputs, call core services in the right order, shape the result.

**Does not belong here:** invariant enforcement that must hold on every path. If a check can be skipped by calling a different operation, it belongs in `core`.

### `src/providers`

One adapter per runtime, plus shared result-schema builders and the dispatcher.

**Belongs here:** everything provider-specific — CLI flags, execution-policy resolution, result decoding, stderr sanitization, capability and version probing.

**Does not belong here:** provider names leaking upward. Core routes by provider identity; it must not know that Codex takes `--sandbox` or that `agy` needs `-p`.

### `src/mcp`

Tool registration, input validation, host-context resolution, error mapping, stdio entrypoint.

**Belongs here:** the translation between protocol and application.

**Does not belong here:** business rules. If MCP is the only thing preventing an illegal state, the check is in the wrong layer — the same operation must be refused when reached another way.

### `src/installer`

The `synaphex` terminal command, per-provider MCP registrars, config lifecycle, installation manifest.

**Belongs here:** installation, registration, and configuration-file rendering.

**Does not belong here:** workflow surface. The installer is deliberately separate from the MCP tools; it registers Synaphex and prepares state, then gets out of the way.

## Entrypoints

| Entrypoint | Source | Audience |
| --- | --- | --- |
| `synaphex` | `src/installer/cli-main.ts` | Users — `install` and `uninstall` only |
| `synaphex-mcp-stdio` | `src/mcp/stdio-main.ts` | Provider MCP hosts, launched by a registration |

Both are declared in `package.json` `bin` and resolve to `dist/`. Each guards its main path with a shared `isProcessEntrypoint()` helper — a real bug class here was an entrypoint check that silently never fired under a global-install symlink, causing exit 0 with no output.

`src/index.ts` is an internal re-export barrel used by tests and the two mains. **It is not a public API**: `package.json` declares `exports: {}`, so there is no supported root or deep import. See [no accidental SDK](#no-accidental-sdk).

## Test organization

Tests live flat in `test/` by concern, not by a unit/integration split:

| Kind | Examples |
| --- | --- |
| Domain and contract | role contracts, rule resolution, error shapes |
| Core service and integration | invocation, staging, apply, locks, ownership races |
| MCP surface | `mcp-read-tools`, `mcp-session-tools`, `mcp-mutation-isolation`, `mcp-server-registration` |
| Real stdio protocol | `mcp-stdio-smoke` — launches a child process and drives it with the official MCP client |
| Provider adapters | per-provider executor, availability, policy, envelope decoding |
| Installer | registrars, planner, config lifecycle, state initializer |
| Live (manual) | `test/live/` — real provider runtimes, never run in CI |

`test/fixtures/` holds shared fixture data. Packed-product testing lives in `scripts/ci/`, not `test/`, because it operates on a built tarball rather than the source tree.

## Contribution boundaries

Structural expectations worth stating explicitly:

- **The public terminal surface is intentionally minimal.** `install` and `uninstall`. Workflow belongs on MCP, not in new subcommands.
- **MCP is the workflow surface.** New user-facing capability is a tool, and a tool is public product surface — see [MCP surface discipline](testing.md#mcp-public-surface-discipline).
- **Package exports are closed.** Adding an export is a product decision.
- **Tests pin public behavior**, not implementation shape.
- **Provider-specific behavior stays behind an adapter.**
- **User state formats need migration discipline** — see below.

### Config lifecycle contract

Changing a config schema or template means honoring the lifecycle established in [ADR 0010](../architecture/0010-package-and-config-surface.md):

```text
parse → validate → preserve semantic values
      → render canonical current comments/template
      → atomic replace
```

Unknown fields are **rejected**, not ignored — silently dropping a field the user wrote is data loss. A file that fails to parse is left byte-for-byte untouched rather than rewritten.

**Related:** [configuration overview](../configuration/overview.md).

### State compatibility

Everything under `~/.synaphex` is durable user state: project and task metadata, plans, memory, bindings, the installation manifest, change sets, and decision receipts.

**There is no general migration framework in v0.1.** When changing any persisted shape, you are responsible for what happens to existing state — whether old records still parse, what a partially written record means, and whether recovery paths still classify correctly. Change-set metadata already carries an optional `resultTree` precisely because earlier change sets lacked it and had to stay readable.

**Related:** [filesystem layout](../reference/filesystem-layout.md).

### No accidental SDK

`package.json` declares:

```json
"exports": {}
```

There is no supported root or deep import path. Exposing an SDK later would be an explicit product and API-stability decision — including what the compatibility promise is — not something that should happen by adding an export field in passing.
